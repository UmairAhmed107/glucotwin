# GlucoTwin: Build Specification (for Antigravity IDE)

A personalised Type 2 diabetes digital twin with new-data entry, prediction, simulation, and personalised intervention and medication-option recommendations.

**How to use this document:** give Antigravity this whole file as context, then run the phase prompts in Section 14 one at a time. Do not paste everything as one prompt.

---

## 1. Product summary

GlucoTwin creates a virtual copy ("twin") of a diabetic patient. The twin:

1. Is **created** from a clinical profile.
2. **Learns** from every new meal, glucose reading and activity entry the user logs.
3. **Predicts** glucose response to meals.
4. **Simulates** what-if scenarios (lifestyle with the trained models; therapy as clearly labelled projections).
5. **Recommends** a personalised plan: meal and activity interventions plus medication options to discuss with a clinician.
6. **Explains** every recommendation and shows where it came from.

Positioning line: *"A hybrid, personalised diabetes digital twin with clinician-in-the-loop decision support."*

## 2. Core design principle: three engines plus provenance

| Engine | Source | Responsible for |
|---|---|---|
| Metabolic Twin | Trained pkl models (real) | Meal-response prediction, lifestyle what-ifs, uncertainty |
| Clinical Reasoning Engine | Gemini API plus guideline snippets | Medication-class options, intervention plan, rationale |
| Safety Governor | Deterministic Python rules | Validates and blocks unsafe or malformed output |

Every card in the UI carries a provenance badge:

- `TWIN-PREDICTED`: produced by the trained models
- `GUIDELINE-BASED (AI)`: generated by Gemini from guideline context
- `SAFETY-CHECKED`: passed the Safety Governor
- `PROJECTION`: literature-informed range, not a model prediction

Gemini never produces twin predictions. This rule is implemented in code, not just in the prompt.

## 3. Assumptions (edit these if wrong)

- A1. `twin_recommender.pkl` holds a `MealRecommender` object (15-model bootstrap ensemble of `HistGradientBoostingRegressor`, feature bounds `lo`/`hi`).
- A2. `meals_db.pkl` is a DataFrame of 1,200 meals from 45 CGMacros participants with columns including: participant id, `gap_prev_min`, `gap_next_min`, `mem_mean_rise`, `mem_mean_iauc`, `mem_n`, `peak_rise`, `iauc_2h`, `delta_60`, `delta_120`, `pre_glucose`, `pre_trend30`, `hour_sin`, `hour_cos`, plus meal macros.
- A3. `shanghai_clinical.pkl` holds 109 patients: `age`, `sex`, `bmi`, `fasting_glucose_mgdl`, `hba1c_pct`, hypoglycaemia flag.
- A4. The user will paste the `MealRecommender` class source and its `predict` method's expected input columns into `/backend/app/twin/twin_engine.py`. **Do not guess these; use placeholders marked `# TODO(USER)` until supplied.**
- A5. The two datasets are different people. Never join them. Shanghai provides clinical context and the profile library; CGMacros provides meal-response history.
- A6. Gemini is called through the Google Generative AI API with the key in `.env` as `GEMINI_API_KEY`.
- A7. Runs locally for demo (laptop), optionally via Docker Compose.
- A8. English only. No language toggle.

## 4. Tech stack

- **Backend:** Python 3.11, FastAPI, Pydantic v2, SQLAlchemy plus SQLite, pandas, scikit-learn (pin the exact version used in Colab), joblib/pickle, `google-generativeai` (or `google-genai`), ReportLab or WeasyPrint for PDF.
- **Frontend:** React plus Vite plus TypeScript, Tailwind CSS, shadcn/ui, Recharts, React Router, TanStack Query, Framer Motion for animation.
- **Testing:** pytest, Vitest (light), a few Playwright smoke tests optional.
- **Packaging:** Docker Compose (backend, frontend), `.env.example`.

## 6. Data model (SQLite)

- **patients**: id, display_name, is_synthetic (bool), source (`cgmacros` | `shanghai_profile` | `new`), cgmacros_participant_id (nullable), age, sex, bmi, hba1c_pct, fasting_glucose_mgdl, hypoglycemia_history (bool), kidney_flag (bool, user-entered), current_meds (JSON list of drug classes), created_at.
- **meal_entries**: id, patient_id, logged_at, carbs_g, protein_g, fat_g, fibre_g (nullable), calories, pre_glucose, pre_trend30, observed_peak_rise (nullable), observed_iauc_2h (nullable), observed_delta_60 (nullable), observed_delta_120 (nullable), activity_after_min (nullable).
- **glucose_readings**: id, patient_id, ts, value_mgdl, source (`manual` | `replay`).
- **twin_state**: patient_id, mem_mean_rise, mem_mean_iauc, mem_n, confidence_score, updated_at.
- **recommendations**: id, patient_id, created_at, kind (`meal` | `lifestyle` | `therapy`), provenance, payload JSON, governor_result JSON.
- **audit_log**: id, patient_id, ts, endpoint, inputs_hash, model_version, rules_triggered JSON, gemini_model, gemini_used (bool).

## 7. Twin engine (real models)

### 7.1 Loading
- Import the `MealRecommender` class **before** unpickling. Load once at startup and expose a singleton.
- Log scikit-learn version at startup and compare against `metrics/validation.json -> sklearn_version`; warn on mismatch.

### 7.2 Twin memory (`memory.py`)
- When a patient with observed outcomes logs a meal, recompute `mem_mean_rise`, `mem_mean_iauc`, `mem_n` as running means over their meals **prior to the current meal** (same convention as `meals_db`).
- New patient: `mem_n = 0`, memory means fall back to the population means from `meals_db` (documented, and flagged in the UI as "population baseline").
- `confidence_score` = a simple monotonic function of `mem_n` plus ensemble spread (for example `1 - exp(-mem_n/5)` blended with narrowness of the 10th-90th band). Document the formula in the UI tooltip.

### 7.3 Predict
Input: meal macros, time of day, pre-glucose, pre-trend, patient memory.
Output per target (`peak_rise`, `iauc_2h`, `delta_60`, `delta_120`): ensemble median, 10th and 90th percentile, min, max.
**Bounds guard:** if any input feature lies outside `[lo, hi]`, return `status: "out_of_range"` with the offending features, and do not return a prediction.

### 7.4 What-if
Supported interventions (mirror the pickled recommender):
- `carb_reduction_pct` (0-50, step 5)
- `post_meal_walk` (bool; duration in minutes if the model supports it, else a fixed value per the recommender)
Recompute calories at 4 kcal/g carbs and protein, 9 kcal/g fat. Return baseline vs intervention predictions, `gain` (rise reduction) per ensemble member, `pessimistic_gain` (10th percentile), and `label: "supported" | "not_supported"` using the 15 mg/dL margin from the recommender.

### 7.5 Additional features built on the same predict call
- **Meal comparison:** 2-4 candidate meals ranked by median predicted peak rise with bands.
- **Best-time-to-eat:** sweep time of day over 24 hours (via `hour_sin`/`hour_cos`) for a fixed meal.
- **Daily planner:** breakfast, lunch and dinner predictions in sequence; flag the worst meal. (Note the model assumes no meal overlap within a 2-hour window; warn when entered meals are closer than that.)
- **Cohort comparison:** percentile of the patient's `mem_mean_rise` against the 45 CGMacros participants.

## 8. Clinical Reasoning Engine (Gemini)

### 8.1 Inputs
A patient JSON containing: age, sex, BMI, HbA1c, fasting glucose, hypoglycaemia history, kidney flag, current medication classes, twin summary (`mem_n`, mean rise, mean iAUC, worst meals, best time of day), plus 3-5 retrieved guideline snippets with ids.

### 8.2 Output JSON schema (enforce with Pydantic; reject on mismatch)
```json
{
  "therapy_options": [
    {
      "drug_class": "string from allowed list",
      "rationale": "string",
      "patient_factors_used": ["string"],
      "expected_effect_literature": "string (population-level, e.g. typical HbA1c change)",
      "cautions": ["string"],
      "monitoring": ["string"],
      "guideline_ids": ["string"]
    }
  ],
  "lifestyle_interventions": [
    {"title": "string", "detail": "string", "linked_twin_finding": "string or null"}
  ],
  "red_flags": ["string"],
  "questions_for_clinician": ["string"],
  "missing_information": ["string"]
}
```

### 8.3 System prompt (put in `prompts.py`)
```
You are a clinical decision-support assistant inside a research prototype.
Use ONLY the patient JSON and guideline excerpts provided.
Return a single JSON object matching the schema. No markdown, no extra text.
Rules:
- Suggest therapy CLASSES to discuss with a clinician, never doses or brand instructions.
- Do not invent patient data. If something needed is missing, list it in missing_information.
- Do not state numeric predictions about this patient. Only describe typical population-level effects and label them as such.
- Reference guideline_ids for every therapy option.
- Respect hypoglycaemia_history and kidney_flag in your reasoning.
- Phrase everything as options for a clinician to review.
```

### 8.4 Allowed drug-class list (config)
`metformin`, `sglt2_inhibitor`, `glp1_receptor_agonist`, `dpp4_inhibitor`, `thiazolidinedione`, `sulfonylurea`, `basal_insulin`. The Governor decides which are permitted for a given patient.

### 8.5 Therapy scenarios ("projections")
For each therapy option the UI shows a literature-based range (taken from the Gemini field `expected_effect_literature`) as a **PROJECTION** card. Do **not** feed these into the trained models and do **not** draw them as model-predicted curves. If a trajectory chart is shown, draw it as a shaded range with the label "Projection from population literature, not a twin prediction".

## 9. Safety Governor (`governor.py`, deterministic, unit-tested)

Runs on every Gemini response before display. Rules:

1. **Schema:** valid against the Pydantic schema, else retry once, else fallback.
2. **Allowed classes:** any `drug_class` outside the allowed list is removed.
3. **No dosing language:** regex rejects mg/mcg/units/"twice daily"/"start with"/"prescribe" in any text field; offending items are removed or the response is regenerated.
4. **Hypoglycaemia history = true:** remove `sulfonylurea` and `basal_insulin` options; add a red flag note; suppress carb-reduction beyond 30% in meal suggestions.
5. **Kidney flag = true:** remove `metformin` and `sglt2_inhibitor` options pending clinician review, or demote them with an added caution (choose one behaviour and document it).
6. **Missing critical data** (no HbA1c, or no age): return the conservative fallback.
7. **Guideline ids** must exist in `/guidelines`; options with unknown ids are removed.
8. **Provenance stamping:** the Governor attaches `{"provenance": "GUIDELINE-BASED (AI)", "safety_checked": true, "rules_triggered": [...]}`.
9. **Twin boundary:** any text field that contains a patient-specific numeric prediction (regex for "your glucose will" or mg/dL predictions) is stripped.

`fallback.py` returns a fixed, conservative plan: lifestyle guidance, monitoring, and "discuss therapy review with your clinician".

## 10. API specification

All responses include `provenance`, `model_version`, and `audit_id` where relevant.

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | Liveness, model load status, sklearn version |
| GET | `/system/models` | Model registry (name, version, training data, metrics) |
| GET | `/system/validation` | Contents of `validation.json` |
| POST | `/patients` | Create patient (new / from CGMacros participant / from Shanghai profile) |
| GET | `/patients` | List |
| GET | `/patients/{id}` | Profile plus twin_state |
| POST | `/patients/{id}/meals` | Log meal (and optional observed outcomes); recompute twin memory |
| POST | `/patients/{id}/readings` | Log glucose reading |
| GET | `/patients/{id}/timeline` | Merged events (meals, readings, recommendations) |
| POST | `/patients/{id}/predict` | Meal response prediction with bands |
| POST | `/patients/{id}/whatif` | Lifestyle what-if |
| POST | `/patients/{id}/compare-meals` | Rank candidate meals |
| GET | `/patients/{id}/best-time?meal=...` | Time-of-day sweep |
| POST | `/patients/{id}/daily-plan` | Plan evaluation |
| GET | `/patients/{id}/cohort-position` | Percentile vs cohort |
| POST | `/patients/{id}/clinical-plan` | Gemini plus Governor, returns therapy options and interventions |
| POST | `/patients/{id}/plan` | Combined 4-week plan (twin findings plus clinical plan) |
| GET | `/patients/{id}/report.pdf` | PDF report |
| POST | `/replay/{participant_id}/start` | Start CGM replay (SSE or polling) |
| GET | `/audit/{audit_id}` | Audit detail |

Use proper HTTP errors; return `422` for `out_of_range` inputs with the feature list.

## 11. Frontend

### 11.1 Design system
- Dark teal/slate theme with one accent colour, light mode optional. shadcn/ui plus Tailwind. Inter font. Consistent chart palette: baseline = grey, intervention = accent, band = accent at 15% opacity.
- Left sidebar navigation, top bar with patient switcher and a persistent banner: **"Research prototype, not a medical device."**
- Provenance badges are a reusable component used on every card.
- Subtle Framer Motion: curves redraw smoothly on slider change; a "Twin updated" pulse after data entry; skeleton loaders.

### 11.2 Pages
1. **Patient Setup:** create new, load a CGMacros participant, or pick a Shanghai-style clinical profile. Demo patients labelled "Synthetic demo patient".
2. **Twin Overview (home):** profile summary, twin-confidence ring, latest forecast, top recommendation, alerts.
3. **Log Data:** meal form (macros, time, pre-glucose, trend, optional observed outcomes), glucose reading form. On save, show a before/after diff of twin state.
4. **Prediction:** meal response curve metrics with bands; "out of range" state shown as an explanatory card.
5. **Twin Learning:** the key demo page. Chart of prediction error or band width versus `mem_n` for a chosen participant (computed from `meals_db` with real values), plus the live patient's memory counter.
6. **What-If Lab:** sliders and toggles, side-by-side curves, `pessimistic_gain`, supported/not-supported badge.
7. **Meal Tools:** compare meals, best time to eat, daily planner.
8. **Clinical Plan:** therapy options to discuss (with GUIDELINE-BASED (AI) and SAFETY-CHECKED badges), lifestyle interventions, red flags, questions for the clinician, and the sources panel listing guideline snippets used.
9. **Therapy Scenarios:** PROJECTION ranges with the mandatory disclaimer.
10. **4-Week Plan and Care Pathway:** a timeline from current state to recommended steps to review points.
11. **Timeline:** HbA1c/glucose/meal/med events.
12. **Cohort:** patient's position versus the 45 participants.
13. **Validation and Model Registry:** real metrics, calibration plot, limitations section.
14. **Clinician View:** denser layout with rationale, rules triggered and audit trail; PDF download.
15. **Live Replay:** CGM replay of a real participant, labelled "Replay of recorded data".

### 11.3 Patient and clinician modes
A toggle switches between plain-language summaries (Gemini-rewritten from the structured plan, with the same Governor checks) and the technical view.

## 12. Validation (must use real numbers from Colab)

The user exports these from Colab into `metrics/validation.json`:
- Participant-grouped CV: MAE and RMSE for each target, population baseline vs personalised twin.
- Error versus `mem_n` (the personalisation curve).
- Ensemble interval calibration (nominal vs empirical coverage).
- `sklearn_version`, training date, row and participant counts.
- Segmented error by HbA1c class if available from the Shanghai-based segmentation.
- Honest limitations: 45 participants, healthy and T2D mix (confirm), meal-isolated windows only, no medication effects learned.

The Validation page only renders values present in this file; it never invents metrics. If the file is missing, show "Validation metrics not yet loaded".

## 13. Testing and quality

- pytest: memory feature computation, bounds guard, what-if calorie math, Governor rules (each rule has a positive and negative test), schema validation, API smoke tests.
- Governor test cases must include: dosing language, forbidden drug for hypoglycaemia history, unknown guideline id, missing HbA1c.
- Gemini calls are mocked in tests; provide `MOCK_GEMINI=true` for offline demo, returning a canned schema-valid response clearly stamped "Demo fixture".
- Docker Compose runs the whole stack with one command. README includes setup, env vars and demo script.

## 15. Demo script (5 minutes)

1. Open Twin Overview for a brand-new synthetic patient: confidence ring at 0, wide bands.
2. Log three meals with observed responses: watch twin state update and bands narrow.
3. What-If Lab: reduce carbs 30% plus post-meal walk; show `pessimistic_gain` and the supported badge.
4. Clinical Plan: show therapy options to discuss, badges, sources, and the Governor's triggered rules.
5. Validation page: personalisation curve and calibration.
6. Close with the limitations slide.
